that it is the stronger opponent. Mini random play is heavily defender-favored,
so aggregate win rates can obscure poor attacker play.

## Recommended next work

### 1. Deliver one reproducible mini training experiment

Build a small CPU-first PyTorch policy/value model with checkpoint loading,
seeded data collection, a short training command, and an evaluation command.
Keep training dependencies optional so the engine remains dependency-free.
This follows the already-recorded project direction; GPU scaling can wait until
the full experiment works.

Implementation order:

1. Extend evaluation around the existing match/replay functions: run the candidate
   against random, heuristic, and fixed-budget MCTS on **both** sides, using
   held-out seeds. Save ruleset, code revision, checkpoint identity, budgets,
   wins/losses/draws/truncations, and decision timing in every report.
2. Define a history-aware input contract, then add a small shared board encoder,
   a 200-action policy head, and an explicit-perspective value head. Retain
   repetition-relevant history; the existing seven board planes alone are not
   Markov. Apply legal masks during training and inference, consistent with
   [PettingZoo's masking interface](https://pettingzoo.farama.org/tutorials/custom_environment/3-action-masking/).
3. Bootstrap with seeded reference-policy games, then add bounded self-play
   updates and an opponent/checkpoint pool. Learn value targets from actual
   terminal outcomes. A collection cutoff has an unknown result and must not
   silently become a draw or zero-value terminal label.
4. Save model, optimizer, RNG state, configuration, and data provenance so a run
   can resume and a saved checkpoint can play through the existing `Policy` interface.

Acceptance: a documented CPU command creates a checkpoint; a fresh process loads
it, plays only legal moves, and emits replay-verified evaluation reports on both
sides. Show learning on held-out seeds across multiple training seeds before
claiming improved strength. Success of the pipeline and superiority to the
heuristic are separate milestones.

### 2. Integrate the verified foundation into the default branch

Prepare a reviewable PR for the existing five-commit modernization branch,
including the retained Copenhagen limitations and the legacy-code boundary.
Keep `main` discoverable and runnable for future clones. This is a small,
independent housekeeping task; no merge or PR was performed during setup.

### 3. Build the human/AI vertical slice

After checkpoint loading works, add the Albion-inspired board UI: move selection,
legal-move highlights, turn/outcome display, replay export, and a choice of human,
heuristic, MCTS, or trained opponent. Use the engine as the rule authority and
bound AI computation. Start with mini to validate the complete play flow; expose
Copenhagen only with its experimental profile identity and limitations.

### 4. Expand Copenhagen adjudication and training

Collect independently adjudicated fort/endgame fixtures, especially forts needing
mobile defenders, and specify or solve the remaining dead-position conventions.
Preserve old ruleset/replay versions when behavior changes. Then measure larger
board search cost and training behavior. Current 11×11 random truncations are a
reason to measure episode collection carefully, not to relabel cutoffs as draws.

The immediate next coding task is the mini training/evaluation pipeline. More
engine rebuilding is not needed to start that milestone.
